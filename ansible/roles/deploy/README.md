# Роль `deploy`

Выкатывает приложение healthchecks: обновляет код из GitHub, ставит зависимости, пишет конфигурацию с актуальными реквизитами базы, выполняет миграции и запускает приложение за nginx. Запускается плейбуком `deploy.yml` на инстансах с тегом `Role=app` — **при каждом релизе**.

```
ALB ──80──> nginx ──127.0.0.1:8000──> gunicorn (hc.wsgi) ──5432──> PostgreSQL
```

## Порядок задач и почему он такой

| # | Файл | Что | Почему здесь |
|---|---|---|---|
| 1 | `tasks/main.yml` | подключить `values/main.yml` | каталог `values/` не стандартный, Ansible его сам не читает |
| 2 | `tasks/envs.yml` | прочитать Parameter Store, записать `app.env` | следующему шагу нужен URL репозитория |
| 3 | `tasks/packages.yml` | `git`, зависимости и gunicorn в venv | код должен быть на месте до генерации настроек |
| 4 | `tasks/main.yml` | **модуль `django_configurator`** — `hc/local_settings.py` | после кода: файл кладётся в каталог приложения; до миграций: `migrate` подключается к базе по этим настройкам |
| 5 | `tasks/migration.yml` | `compress` → `collectstatic` → `migrate` | порядок из README приложения; до запуска, чтобы новый код не стартовал со старой схемой |
| 6 | `tasks/run-server.yml` | systemd-служба, конфиг nginx, перезапуски, проверка | запуск — последним, когда всё готово |

Если поменять местами шаги 4 и 5, при первом деплое `migrate` не нашёл бы настроек PostgreSQL и применил бы миграции к локальному SQLite-файлу.

## Входы

**Снаружи** — из инвентаря или `ExtraVariables` ассоциации State Manager:

| Имя | Пример | Описание |
|---|---|---|
| `ssm_param_prefix` | `/week4/dev` | префикс параметров |
| `aws_region` | `eu-central-1` | регион Parameter Store |
| `app_version` | `main` | ветка, тег или коммит |
| `deployment_environment` | `production` | `production` выключает `DEBUG` |

**Из Parameter Store:** `db_host`, `db_name`, `db_user`, `db_password` (SecureString), `app_repo`, `django_secret_key` (SecureString), `alb_dns_name`.

**`defaults/main.yml`:**

| Имя | По умолчанию | Описание |
|---|---|---|
| `app_user` | `django` | пользователь приложения |
| `app_dir` | `/opt/django-sample-app` | корневой каталог |
| `app_src` | `{{ app_dir }}/src` | код приложения |
| `app_venv` | `{{ app_dir }}/venv` | виртуальное окружение |
| `app_env_file` | `{{ app_dir }}/app.env` | переменные окружения приложения |
| `app_port` | `8000` | порт gunicorn на `127.0.0.1` |
| `app_version` | `main` | запасное значение |
| `deployment_environment` | `production` | запасное значение |
| `django_additional_settings` | `{}` | запасное значение |

**`values/main.yml`** — параметры конкретного выката, подключаются через `include_vars` и поэтому перебивают инвентарь:

| Имя | Значение |
|---|---|
| `gunicorn_version` | `26.2.0` |
| `gunicorn_workers` | `3` |
| `django_additional_settings` | `SITE_NAME: Week 4 Healthchecks` |

## Пример

```yaml
---
- name: Deploy application
  hosts: all
  become: true
  serial: 1
  roles:
    - deploy
```

```bash
ansible-playbook -i inventory.ini deploy.yml --limit webservers
```

## Требования

- роль `webserver-setup` уже применена: Python 3.12, venv, nginx, пользователь `django`
- модуль `django_configurator` в `ansible/library/` рядом с плейбуком
- база настроена ролью `postgres-setup`

## Конфигурация приложения: два файла

| Файл | Кто пишет | Что внутри | Права |
|---|---|---|---|
| `hc/local_settings.py` | модуль `django_configurator` | `DATABASES`, `DEBUG`, `ALLOWED_HOSTS`, `SITE_NAME` | `root:django 0640` |
| `/opt/django-sample-app/app.env` | шаблон `app.env.j2` | `SECRET_KEY`, `SITE_ROOT` | `root:django 0640` |

`settings.py` приложения подключает `local_settings.py` в самом конце, поэтому значения модуля перебивают значения по умолчанию. Но `SITE_ROOT` должен прийти из окружения: `settings.py` вычисляет из него `PING_ENDPOINT` и `STATIC_URL` при импорте, раньше, чем подключится `local_settings.py`. `SECRET_KEY` оставлен в окружении, чтобы не передавать секрет через `additional_settings` — модуль маскирует в выводе только пароль базы.

Права `root:django 0640`: приложение читает файлы, но изменить их не может.

`ALLOWED_HOSTS` — адрес балансировщика и приватный IP сервера: health check балансировщика приходит с приватным IP в заголовке `Host`.

## Миграции на двух серверах

Серверов приложения два, база одна, а межпроцессной блокировки миграций в Django нет. Решение — **выкатка строго по одному серверу**: первый применяет миграции, на втором `migrate` печатает `No migrations to apply`.

- через SSM — `max_concurrency = "1"` у ассоциации `deploy`
- с машины — `serial: 1` в `deploy.yml`

`run_once` не подходит: через SSM каждый сервер запускает плейбук сам для себя и соседа не видит. Флаг `run_migrations=true` для одного сервера тоже отвергнут: пересоздали этот сервер — миграции тихо перестают выполняться.

`max_errors = "0"` останавливает выкатку на первой ошибке: второй сервер остаётся на старой версии и обслуживает запросы. Поэтому миграции должны быть обратно совместимыми — пока выкатывается первый сервер, второй работает на старом коде с новой схемой.

## Что здесь неочевидно

**Команды `manage.py` читают секреты из файла, а не из `environment:`.** Значения `environment:` Ansible подставляет в строку команды, и на `-vvv` они видны в выводе. `set -a && . app.env` читает их уже на сервере.

**Обработчики nginx в паре.** `Проверка конфига nginx` (`nginx -t`) и `Перечитать конфиг nginx` слушают одно событие `Reload nginx` и выполняются в порядке объявления. Сам `nginx -s reload` возвращает успех даже с битым конфигом — без проверки ошибка осталась бы незамеченной.

**Роль проверяет себя.** Последняя задача запрашивает `/api/v3/status/` по приватному IP сервера — ровно как health check балансировщика. Эндпоинт выполняет `SELECT 1`, поэтому проверяется вся цепочка: nginx, gunicorn, Django, база. С `serial: 1` второй сервер не начнёт выкатку, пока первый не ответит.

**Статику отдаёт приложение.** В `settings.py` подключён WhiteNoise, поэтому в `nginx.conf` нет `location /static/` и нет путей, которые надо держать в синхронизации.

**Заголовок `X-Forwarded-For` обязателен.** README приложения требует его от прокси: без него клиент может подставить свой IP и обойти ограничение частоты попыток входа.

**`changed_when` у команд.** `migrate` — изменение, только если в выводе нет `No migrations to apply`; `collectstatic` — если скопировано больше нуля файлов; `compress` всегда `false`: результат детерминирован, реальные изменения видны по задачам `git` и `collectstatic`.

**Идемпотентность.** Повторный запуск через SSM: `ok=17 changed=0`, модуль сообщает `already up to date`.

## Что роль не делает

- **не снимает сервер с балансировщика на время выката** — пока gunicorn перезапускается, часть запросов к этому серверу может получить ошибку
- **не откатывается** при неудаче — остановка выкатки на первой ошибке защищает остальные серверы, но не возвращает первый
- не закрепляет версию: по умолчанию выкатывается ветка `main`, а не тег
- не запускает `manage.py sendalerts` — процесс рассылки уведомлений, который README приложения требует держать запущенным; задание его не упоминает
- не настраивает почту — вход и регистрация по ссылке из письма не работают, пользователь создаётся командой `manage.py createsuperuser`
